## 2. Приоритетные проблемы

P1 — блокирует важный сценарий или угрожает целостности данных. P2 — заметная ошибка/ограничение, которое нужно устранить до полноценной приёмки. «Не реализовано» — отдельная незавершённая функциональность, не регрессия старой.

### A01 · P1 · Частичное сохранение спринта и дубли при повторе — К

Сначала создаётся/публикуется сам спринт, затем отдельными последовательными запросами записываются правила и задания. Полученные ID новых связей не сохраняются в локальный baseline. Если второй/следующий запрос падает, предыдущие уже выполнены; повтор может создать ещё один спринт, продублировать задания/правила либо упереться в запрет второго активного спринта.

Сценарий проверки: два задания → первое создалось, второе вернуло ошибку → повторить «Запустить». Нужна безопасная повторная попытка с сохранением прогресса/ID. Атомарный серверный endpoint полезен, но фронтовую защиту от дублей можно сделать без ожидания нового API.

Источник: [сохранение связей](</Users/maxiqqq/Developer/collabox/admin-frontend/src/pages/(list_integration)/sprints/slug/index.tsx:600>), [публикация до связей](</Users/maxiqqq/Developer/collabox/admin-frontend/src/pages/(list_integration)/sprints/slug/index.tsx:787>).

### A05 · P1 · Итоги спринта представлены полнее, чем позволяет реальный API — Б, К, API, F

### A12 · P2 · Превью наград нарушает сумму пула — Б, К, Т

- Пересечения диапазонов: `.find` учитывает только первое подходящее правило. Для «1 место → 10» и «1–3 → 20» показывает 10 вместо 30.
- Пропорциональные доли округляются независимо. Для одного неделимого приза и двух равных участников получается 1+1=2; для трёх — 0+0+0.
- В браузере на существующем редакторе видны доли 2632 + 1316 + 1053 = **5001** из пропорционального пула 5000.
- При одинаковом XP локальное превью назначает разные места, хотя DTO рейтинга обещает одинаковое место.

Локальность превью правильна и была специально запрошена пользователем. Исправлять нужно именно математику общего компонента и согласовать детерминированное распределение остатка/равных мест с сервером.

[Источник расчёта](</Users/maxiqqq/Developer/collabox/admin-frontend/src/pages/(list_integration)/sprints/slug/components/SprintCreationStepTwo.tsx:512>), [семантика мест](</Users/maxiqqq/Developer/collabox/admin-frontend/src/api/generated/model/leaderboardEntryDto.ts:11>).

### A14 · P2 · В редакторе, sidebar и рейтинге используются разные правила суммы — Б, К, Т

Sidebar суммирует amount без количества мест byRank: 2–5 места по 2 футболки → 2 вместо 8. Денежные подписи местами берутся из имени награды, а не количества. `name:"1000 ₽",amount:3` превращается в 1000. ## 5. Вопросы к продуктовой логике самого макета

1. **Событие vs спринт/конкурс.** Секция названа «Промокоды Спринт / Конкурс», но внутри выбран раздел «События», шаг называется «Настройка спринта», а CTA — «Создать событие». Надо определить единую модель, не копировать смешанные подписи буквально.
2. **Персональный или общий промокод.** SALE200 один на событие или это пример личного кода исполнителя? Кто получает XP/деньги — владелец или активировавший?
3. **Что означает «Подтвердить выдачу».** Отметить уже переданный вручную приз или инициировать выплату? Это принципиально разные действия и требования к API.
4. **Счётчики early review.** «7 участников» — уникальные люди или число незавершённых выполнений? Один человек может выполнять несколько заданий. До подтверждения нужна корректная серверная сводка последствий.
5. **Пропорциональное деление и равные места.** Куда уходит остаток, кто получает неделимую единицу, как учитываются равные XP и пересечения правил? Нужен единый алгоритм для сервера и локального preview.
6. **Пул неконкурса.** В примерном макете выбрано 6 участников, награда 1000 ₽ каждому, sidebar показывает 124000 ₽. Возможно, демонстрационные числа; их нельзя использовать как спецификацию расчёта. Уточнить базу: выбранные/приглашённые/одобренные/завершившие участники.
7. **Смена профиля ОРД.** Сохранить прежний сценарий блокировки после актов или заменить его новым «Сменить статус → новая компания»? Изменение имени/телефона и смена статуса должны быть различимы.

## 6. Что уже работает и чего не нужно «чинить» повторно

- «+» спринта открывает третий шаг редактора, а не индивидуальные задания.
- Freeze/unfreeze подключены к реальному API, есть подтверждение/ошибки. Старые записи кэша об отсутствии endpoint устарели.
- Черновики, description спринта, версии наград, дробные количества, tasksToReviewCount и принадлежность задания sprintId уже поддержаны контрактом.
- Каталог наград и локальное preview используют общий компонент. Отдельная несохраняемая модель preview — требование пользователя, не backend gap.
- Участники загружаются по всем страницам перед поиском; защищена отмена одного человека из multi-target приглашения; не придумываются имена отсутствующих в API пользователей.
- Иностранные реквизиты ОРД и demo-команда ограничены dev-provider; неподдерживаемые реквизиты не отправляются в production DTO. Это согласованная граница, а не скрытый дефект.
- Индивидуальные задания удалены намеренно; старые макеты 16634/16630 не следует возвращать автоматически.
- Senler.io `postMessage` был сознательно отложен пользователем; не включён в список случайных регрессий.

## 7. Почему мок-стенд пока недостаточен для приёмки
