## Реализация

Общий экран `/rooms/:slug/applications`, включая обычные development/production и мок-стенд. Использованы @senler/ui, существующие mutation hooks и Orval-клиент. Отдельная HTML-верстка не создавалась.

- Команда / Исполнители; Активные / Заявки / Приглашения; поиск без учёта регистра; пустые/loading/error состояния; клиентская пагинация.
- Загружаются все страницы перед поиском — не только первая. До серверного поиска это линейная загрузка, потенциально дорогая для крупных компаний.
- Имена исполнителей из RoomApplication.name; аватары и ссылка VK из BaseAmbassadorDto. Иконка профиля открывает VK, не вымышленный внутренний профиль.
- Заявки: PATCH `/api/ambassador/room-applications/status` через существующий app hook.
- Добавление исполнителя: POST `/api/invitations/parse-vk-user-id`, затем POST `/api/invitations` с `channelTypeId: 1` (по DTO; не 0).
- Приглашения: только необработанные targets. Без выдуманных ФИО/аватаров: `VK · id` / `Telegram · id` и fallback.
- Отмена одиночного приглашения через DELETE `/api/invitations/{id}`. Для группового приглашения действие отключено: нельзя удалить всех по клику на одного человека.
- Команда на стенде: тот же UI, демо-данные передаются только dev-entry через TeamPreviewContext. Роли, добавление и удаление демо-команды хранятся только в памяти страницы и явно обозначены. Никаких вымышленных endpoint для команды нет. Без dev-provider обычное приложение показывает недоступность команды.
- Владелец не удаляется и его роль не меняется даже в демо.
- Старая обработка заявок по компании/событиям сохранена, доступна из вкладки команды («Ранее созданные заявки»).

## Чего не хватает в backend

Сверено с публичным свежим Swagger `https://api-ambassador.senler.ru/api/docs-json` 2026-09-15; generated-файлы в этой задаче не менялись.

1. **Команда компании**: список участников, имя/аватар/VK-профиль, роль `owner/admin/editor/viewer`; добавление по VK, смена роли, удаление. Нужны серверные проверки полномочий и защита владельца. Сейчас соответствующих DTO/endpoint нет.
2. **Удаление активного исполнителя из компании**: отдельная операция на связи участник—компания. Перевод заявки в rejected не подменяет удаление участника.
3. **Приглашённый пользователь**: имя, avatarUrl, profileUrl в InvitationTargetDto или отдельное получение профиля. Сейчас там только id, channelTypeId, subscriberId, processed, timestamps.
4. **Отмена одной цели группового приглашения**: сейчас удаляется весь контейнер приглашения, нет операции по targetId.
5. **Серверный поиск** по спискам заявок/участников/приглашений для масштабирования. У room-applications и invitations есть пагинация, но нет поиска. У /ambassador есть nameContains (>2 символов), однако он не покрывает заявки и незарегистрированных приглашённых.
